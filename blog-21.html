How I Got Here

Six months ago I was running three AI-powered micro-SaaS products. A Telegram news curator, a daily content pipeline that churned through 500 articles, and a batch analyzer for customer support logs.

All three talked to OpenAI's API. I was paying per token and not thinking about it — until April when my bill hit $312.

I checked the numbers. My Telegram bot alone was generating ~100K queries/month. The content pipeline was burning 30M tokens monthly. Each product had its own API key, its own integration, its own cost center. No aggregation. No caching. No fallback.

The classic solo founder mistake: build fast, optimize never.

The Breaking Point

It wasn't just the money. Three things happened in quick succession:

  1. OpenAI deprecated a model I depended on — one afternoon my content pipeline started returning garbage. I hadn't pinned the model version. Two hours of debugging.
  2. A rate limit spike killed my bot for 45 minutes — no alert, no retry, no queue. Users just got silence.
  3. I added up the annual cost — $3,000/year on API bills for a side project that made maybe $200/month.

That's when I started looking at alternatives.

The Naive First Attempt

My first idea was dumb: "What if I just point everything at a local LLM?"

I spun up a $5 DigitalOcean droplet, installed Ollama, and tried running Llama 3.2 8B. It worked — until the first concurrent request hit. The 1C1G server locked up so hard I couldn't SSH in. I force-rebooted three times in one afternoon.

A friend told me about n8n. Another mentioned Docker Compose resource limits. Someone on Reddit suggested PostgreSQL with connection pooling.

I started reading. A lot.

(Most of what I learned is now documented in the Architecture Blueprint — but here's the short version.)

The Architecture That Worked

After six weeks of trial and error, I settled on a 7-service Docker Compose cluster on a 2C4G VPS:

┌─────────────┐     ┌──────────────┐     ┌──────────┐
│  n8n Engine │────▶│ PostgreSQL   │◀────│  Redis   │
│ (workflows) │     │ (HA + WAL)   │     │ (queue)  │
└──────┬──────┘     └──────────────┘     └──────────┘
       │                                       
       ▼                                       
┌─────────────┐     ┌──────────────┐
│ AI Gateway  │────▶│ Auth Server  │
│ (routing)   │     │ (RSA keys)   │
└──────┬──────┘     └──────────────┘
       │
       ▼
┌─────────────┐
│ Nginx       │
│ (edge/rate) │
└─────────────┘

The key insight: constraints produce better architecture.

With only 2 cores and 4GB RAM, I couldn't afford wasteful abstractions. Every service had to earn its memory. The stack became brutally minimal:

  • n8n handles all workflow logic — scheduling, retries, branching, error handling
  • PostgreSQL stores everything from workflow state to customer logs — with WAL archiving for point-in-time recovery
  • Redis queues bursts so the VPS never OOMs on traffic spikes
  • AI Gateway routes between OpenAI, DeepSeek, and local LLMs — with fallback, rate limiting, and cost tracking
  • Auth Server uses RSA-2048 key pairs bound to machine fingerprints — no external identity provider needed

What I Lost

I'm not going to pretend self-hosting is all upside. Here's what I gave up:

  • Instant scale — if traffic 10× overnight, my VPS will choke. I handle this with Redis queue backpressure and an SQS bridge for overflow. Works well enough.
  • Zero ops — I now spend maybe 2 hours/month on maintenance. Patch the server. Rotate logs. Check backups. Acceptable.
  • Bleeding-edge models — I don't get GPT-5 on day one. But honestly, Qwen2.5 7B and GPT-4o-mini cover 95% of my use cases.

The trade-off was worth it. $2,800/year in savings buys a lot of patience.

What I Gained

  • Fixed cost — $17/month regardless of how much traffic I process. No surprise bills.
  • Zero vendor risk — no API deprecation, no pricing changes, no rate limit anxiety
  • Full audit trail — every API call, every workflow execution, every DB query is logged in-cluster
  • Offline capability — if my internet drops, the cluster keeps running locally
